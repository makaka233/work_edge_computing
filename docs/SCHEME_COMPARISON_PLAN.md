# 五场景方案对比计划

更新时间：2026-08-27  
当前基线分支：`improve-slow-critic-credit-v2`  
当前参考训练：`placement_credit_episode60_large_s30_u320_20260826_123639`

## 1. 当前阶段结论

当前版本先停止继续调参和修改算法。320-update 训练已经证明：

- 训练能够稳定完成，Fast 后期基本可以执行完整的 4 个 PPO epoch，不再持续撞击 KL 早停。
- Slow window critic 的后期 holdout explained variance 约为 0.97--0.98，critic 已不是主要瓶颈。
- 最佳滚动模型出现在 update 307，说明后半程仍能找到更优策略；末尾的短期波动不是不可恢复的崩坏。
- 平均时延在约 update 80 后进入 340--350 ms 的噪声平台。与上一版本严格配对的前 160 updates 相比，平均时延只改善约 0.94 ms，属于结构改善明显、最终性能增益有限。
- 当前最突出的问题是 Slow Count：后期 entropy 约为 0.65、KL 接近 0，平均副本数约为 15.79/16。Count 已接近确定性地选择最大副本数，限制了资源效率和进一步优化空间。
- Placement entropy 约为 1.1，Fast entropy 约为 0.58--0.62；二者没有完全坍缩，但自适应熵系数均接近或达到上限，说明仅继续提高熵系数未必能解决策略表达和信用问题。

本阶段保留以下优化思路，但暂不实施：

1. 将 Count 从“直接输出绝对副本数”改为相对当前部署的增量动作，或采用分层的扩容/保持/缩容决策，降低 1--32 大动作空间造成的边界吸附。
2. 为 Count 使用与资源影子价格相关的约束或拉格朗日目标，使延迟收益和副本成本能够随资源紧张程度自动平衡，而不是继续手工放大固定惩罚。
3. 将“已部署副本数、有效副本数、边际时延收益”明确分开，Count 奖励只评价新增或删除一个副本带来的边际系统收益，避免最大副本数成为安全但无区分度的选择。
4. 在改变 Count 前先检查可行动作 mask、确定性解码和动作分布中心/方差，排除最大可行数随状态变化而产生的隐式标签泄漏或边界偏置。
5. 后续如继续优化，以 `best.pt`（update 307）为性能参考，以 `latest.pt`/`last.pt` 为断点恢复参考，不用单个末尾 update 代替完整滚动成绩。

## 2. 对比目标与边界

本计划比较的是五种可以独立运行、独立训练或独立求解的完整方案，而不是从当前方法中逐项删除奖励、critic、熵控制器或信用模块。

- **方案对比回答**：在相同环境交互预算和相同测试请求下，哪一种完整控制方法更好。
- **消融实验回答**：当前方案中的某一个模块是否有用。消融不纳入本轮五方案主表，后续需要时另立实验。
- 所有方案都继续使用同一环境、同一可行性约束和同一个 KKT 连续资源分配器。KKT 是环境中的公共求解层，不作为某个方案的独占优势。
- 主指标必须从环境统一计算，不能直接比较各算法内部定义不同的训练 reward。

## 3. 五种完整对比方案

| 编号 | 完整方案 | Slow 决策 | Fast 决策 | 学习范式 | 定位 |
|---|---|---|---|---|---|
| A | 当前 Hierarchical Dual-PPO + KKT | Count PPO + Placement PPO，每 10 分钟决策 | GAT node-scorer PPO，逐请求调度 | 双时间尺度 on-policy | 待验证的主方案 |
| B | Centralized MAPPO + KKT | 服务/阶段 actor 产生部署决策 | 服务/阶段 actor 产生路由决策，集中 critic 使用全局状态 | 标准集中训练、分散执行的多智能体方案 | 强 DRL 对照 |
| C | Hybrid Discrete SAC + KKT | 离散 Count/Placement actor 使用 replay | 离散 masked SAC 路由 actor 使用 replay | 双时间尺度 off-policy | 样本效率与稳定性对照 |
| D | Rolling-Horizon Optimization + KKT | 根据最近窗口需求预测，执行容量约束局部搜索或整数规划近似 | 使用预测拥塞的最短时延调度 | 非学习、模型驱动在线优化 | 优化算法对照 |
| E | Greedy Deployment + Greedy Scheduling + KKT | 按需求位置和节点容量贪心部署 | 枚举候选节点并选预测时延最低路径 | 非学习启发式 | 当前已有、可复现下界 |

实施说明：当前代码已具备 A 和 E。B、C、D 尚需作为独立 agent/runner 实现。在它们实现前，不用把 A 的开关组合伪装成这三种方案。若 D 的精确整数规划在 32 节点规模下超时，应固定采用同一时间上限的 rolling-horizon local search，并同时报告最优间隙或超时率。

## 4. 五个环境场景

五个场景均使用 12,000 用户、32 个边缘节点、10 类服务、60 分钟 Episode、10 分钟 Slow 窗口和相同的物理拓扑。场景改变的是运行压力，不改变算法本身。

| 场景 | 目的 | 相对 `mec-moderate` 的关键设置 | 主要观察量 |
|---|---|---|---|
| S1 均衡中等负载 | 复现当前主实验工作点 | 直接使用 `--pressure-profile mec-moderate` | 综合时延、稳定性 |
| S2 宽分布突发负载 | 在均值近似不变时提高 Episode 间负载方差 | `--load-strata "0.55:0.75,0.85:1.05,1.20:1.40,1.65:1.85" --load-stratum-probabilities "0.15,0.40,0.30,0.15"` | 高负载尾部、恢复速度 |
| S3 计算瓶颈 | 让部署容量和计算拥塞主导 | `--task-compute-scale 2.20 --node-compute-capacity-scale 0.45 --task-data-scale 1.50 --wired-link-bandwidth-scale 0.50` | 节点热点、有效副本、deadline |
| S4 网络瓶颈 | 让跨节点传输和拓扑路径主导 | `--task-compute-scale 1.20 --node-compute-capacity-scale 0.90 --task-data-scale 4.00 --wired-link-bandwidth-scale 0.06` | P95、链路热点、跨节点率 |
| S5 部署资源紧张 | 检验副本数量和位置选择是否真正有效 | 保留 S1 负载，仅设置 `--service-resource-fraction 0.18` | 可行率、冗余率、内存/存储占用 |

上述数值是首轮协议值，不是最终宣称值。正式训练前，每个场景先用 E 方案和随机初始化的 A 方案各运行 20 个完整 Episode 做可行性校准。只允许在看到正式结果前统一调整场景强度，目标是：无效动作率接近 0、不能长期落入固定惩罚时延、同时能观察到明确的计算/链路/部署压力。校准完成后冻结场景配置。

## 5. 公平实验协议

### 5.1 训练预算

- 每个学习方案在每个场景独立训练，不能用某方案在 S1 训练、另一方案在 S3 专门训练。
- 正式规模统一为 320 updates；每个 update 采集 2 个完整 60 分钟 Episode，即每次训练 640 Episodes、2,304,000 logical one-second steps。
- 统一使用 `sampled-seconds-per-window=60`；因此每次训练实际执行 230,400 个 settlement steps。若某算法使用 replay，也不能获得额外环境交互。
- 使用 5 个训练种子：2026、2027、2028、2029、2030。显式固定 `physical_seed=2026`，使五个种子只改变初始化、需求、请求和负载随机流，不改变物理基础设施。
- A、B、C 按相同环境交互数比较；同时单独报告墙钟时间和优化器更新次数。D、E 不伪造训练过程，只报告求解/推理时间。

### 5.2 模型选择与测试

- 训练、验证、测试需求种子必须分离。训练流由训练 seed 推进；验证使用固定但不公开给优化器的种子集合；测试使用另一组种子。
- 学习方案统一按验证集滚动平均时延选择 checkpoint，不能让 A 用 `best.pt` 而 B/C 只用最后模型。
- 每个最终 checkpoint 在每个场景的同一批至少 100 个完整测试 Episodes 上运行。每一个 `(scenario, test_seed, episode)` 对所有方案完全配对。
- 测试采用完整 600 settlement seconds/window，不使用训练时的时间抽样；所有方案使用确定性动作，同时可以补充随机策略重复测试，但不能混入主表。
- 如果总计算量过大，先进行“1 seed × 80 updates × 5 场景”的筛选轮；筛选轮只用于排错，不能替代最终统计结果。

### 5.3 指标

主表按场景分别报告：

1. 请求加权平均时延（ms）。
2. 请求级 P95 时延（ms），不能平均各 Episode 的 P95 后冒充全局 P95。
3. Deadline violation rate。
4. 无效/不可行决策率。

资源与工程指标作为第二张表：

- 有效副本数、冗余副本率、空闲副本率。
- 节点/链路平均利用率、热点率和负载标准差。
- 跨节点 stage transition rate、内存和存储使用率、迁移量。
- 每个请求的 Fast 推理时间、每次 Slow 决策时间、总训练墙钟时间和峰值显存。

Reward 曲线只用于解释各学习算法的训练过程。跨方案结论以统一的环境时延、违约率和资源指标为准。

### 5.4 统计与展示

- 对每个场景给出 5 个训练种子的均值、标准差和 95% bootstrap confidence interval。
- 在相同测试 Episode 上使用 paired bootstrap 比较 A 与 B--E，并同时报告绝对差值和相对改善百分比。
- 不只汇报“最佳 seed”；主结果使用 seed 均值，最佳/最差 seed 仅用于解释稳定性。
- 每个场景绘制独立的平均时延和 P95 箱线/小提琴图；另绘制 `场景 × 方案` 的平均排名热力图。
- 训练曲线横坐标统一使用累计环境 logical steps，并在上方标注 Episode；不能只用 update 数掩盖不同方法的采样预算。

## 6. 执行顺序

1. 冻结当前 A 方案和五个场景配置，记录代码 commit、依赖和 GPU 型号。
2. 为所有 agent 定义统一的 `act_slow`、`act_fast`、checkpoint 和 evaluation 接口。
3. 先接入已有 E，建立成对测试数据和统一结果表。
4. 依次实现 D、B、C；每接入一个方案先做单场景 20-Episode correctness run。
5. 运行 1-seed/80-update 筛选轮，排除数值错误和长期不可行状态。
6. 冻结全部超参数后运行 5-seed/320-update 正式矩阵。
7. 生成五场景主表、配对置信区间和计算成本表；消融实验另开文档，不混入本轮结论。

## 7. 预期可回答的问题

完成这套对比后，可以分别回答：

- 当前双时间尺度 PPO 是否优于标准多智能体和 off-policy DRL，而不仅仅优于旧版本自己。
- 性能优势来自正常负载下的平均优化，还是来自突发、计算瓶颈、网络瓶颈或资源紧张时的鲁棒性。
- 学到的 Count/Placement 是否真正提高有效副本利用，还是仅靠接近最大副本数换取时延。
- 相比在线优化和贪心方法，DRL 的时延收益是否足以补偿训练成本、推理复杂度和稳定性风险。
