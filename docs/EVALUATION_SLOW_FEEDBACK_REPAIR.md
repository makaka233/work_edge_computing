# 评估中 Slow 上一窗口反馈修复

修复前版本已备份并上传 GitHub，提交为
`d29a48f65e05ba4ba401a2d4893f407a2392ccf1`，沿用现有分支。
训练日志、评估数据、图片和模型保留在本地，不删除或覆盖。

## 当前选择的方案

参考方案为 Proposed，对比方案为 **DARP、HEFT、DPMS、MSO**。
后续调用应明确指定 `--schemes Proposed DARP HEFT DPMS MSO`。
不改变旧 CLI 的默认方案集合，以免破坏已有命令、旧结果和阶段验证；
Hybrid 保留为旧接口，但不在此次选择与修复覆盖范围内。

## 问题与修复边界

训练时 Slow 使用上一部署窗口的结算反馈。旧 Proposed 和 HEFT 评估适配器
没有汇总这些反馈，第二窗口起仍用空值。MSO 已经有独立汇总实现。
因此运行没有报错、请求轨迹相同，并不保证学习型部署策略的观测接口一致。

本次把 MSO 已有的九项反馈汇总逻辑提取成评估专用共用组件，并接入
Proposed、HEFT、MSO。DARP 仅复用 Fast，DPMS 不使用 PPO，二者不需要
这个 Slow 输入，算法实现不变。没有调整部署或调度目标函数、学习率、
模型权重、奖励定义、节点能力、服务预算、网络约束或公共 KKT 求解器。
Proposed 与 MSO 的训练入口及公共 PPO 更新器均未修改。

## 统一流程

1. Episode 第一个窗口无历史反馈，明确清空，不读检查点或上次评估的残留。
2. 每个结算批次收集本方案自己的真实结算结果，不使用预测时延，也不借用
   其他方案的结果。权重直接使用 `env.step` 的 `group_info.request_count`，
   已含抽样代表间隔，不再重复乘一次代表间隔。
3. 下一次 Slow 决策前，汇总此前窗口的平均时延、加权 P95、平均惩罚时延、
   超时率、无效动作率、节点与链路负载峰值、部署内存与存储占用比例。
4. 资源比例与训练一样按总使用量除以总服务池容量计算，而不是节点比例
   的不加权平均。部署后捕获资源占用，属于该部署窗口，不泄露下次决策。
5. 汇总后清空当前窗口累加器；空窗口产生空反馈，不复用更早的窗口。
   Episode 末尾汇总最后窗口，但不执行额外部署或 PPO 更新。

评估仍冻结策略，调用 `record=False`，不新增 PPO 训练样本或更新模型权重。
MSO 的阶段聚合与完整服务部署规则保留。

## 独立 KKT 资源分配对照

虽然此次五方案选择不包含 NoKKT，已有独立资源分配对照仍需与修复后的
Proposed 控制器一致。其接口也补充观察回调，但只观察 **Proposed KKT
控制器** 的结算结果。等分资源等对照环境不得改变控制器的下一步决策，
部署与调度路径仍作为同一条冻结轨迹回放给各资源分配方式。

## 可追溯记录

新评估的 `metadata.json` 标注：

```json
{
  "slow_window_feedback_protocol": "own-window-weighted-feedback-v1",
  "slow_window_feedback_schemes": ["Proposed", "HEFT", "MSO"]
}
```

`diagnostics/solver.csv` 中 `planner=slow_window_feedback` 的行记录每次
部署前实际传入的反馈。首个窗口 `has_previous_window_feedback=false`；
后续窗口有请求时应为 true，并包含上述九项数值。
这个文件原本记录各类部署诊断，并非仅 MILP 日志。

旧评估数据不改写。此前六负载点 Proposed/MSO 曲线应重新评估后再作为
最终对比结果。现有新环境训练检查点可直接使用，不需要因接口修复重训。

## 仍保留的限制

- DPMS 的默认副本搜索未加速或截断；32 节点测试中单次部署仍可耗时数分钟。
- DPMS/DARP 网络预测是独立链路近似，HEFT 使用经典静态资源估计。
  最终结算仍遵守共享 NIC；本次不把启发式算法改成共享 NIC 的精确优化器。
- 当前评估的请求轨迹和时间采样方式不变；接口修复不证明低抽样率等价于
  完整逐秒模拟，也不保证任何方案的性能排序。

验证包括加权反馈与训练观测一致、窗口边界、空窗口、重复 episode 清理、
MSO 兼容、固定动作下结算不变，以及独立 KKT 回放仍共享完全相同动作。
