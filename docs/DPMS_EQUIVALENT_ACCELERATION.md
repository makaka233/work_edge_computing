- [GitHub 备份](https://github.com/makaka233/work_edge_computing/tree/f8a41db9a7b7bebbe77e93e5996da5455c59940e)

不创建新分支，不删除或覆盖训练、评估、图片与模型产物。
本次仅加速 DPMS 的部署代价计算，并增加实现版本标记。
Proposed、MSO、DARP、HEFT 的策略和训练代码不变；边缘网络、服务预算、
抽样方式与公共 KKT 结算不变。

## 原来慢在哪里

DPMS 先通过 MILP 为每个服务阶段选择一个必需副本，再比较可行额外副本
带来的边际收益。每加入一个副本，该服务所有剩余候选都要重新计算代价。
旧实现每次从头逐个入口节点计算串行服务链，反复构造不变的传输矩阵。
抽样减少请求结算次数，但不会减少每个 10 分钟窗口的一次部署规划，
所以不能解决这个热点。

## 现在怎样加速

1. 在一次 `plan` 内，为每个服务准备有效算力、入口代价、阶段间传输代价、
   汇总算力项的固定分子。改变候选部署时不必重建这些数据。
2. 同时计算所有有需求的入口节点的串行服务链代价；依然遍历每个阶段，
   在所有已部署父节点上取最小值，而不是用固定路径库或缩减候选。
3. 保留原来按入口节点升序累加的顺序，以及每阶段加法、最小值归约顺序，
   避免浮点重排扰动近似相等的优先级。
4. 每次 `plan` 都重新创建缓存。负载、需求、节点能力、带宽、服务阶段、
   数据量及计算量发生变化时，不会复用上一窗口的代价。

默认仍使用所有节点和全部可行额外副本搜索：`candidate_nodes=0`、
`max_additions=0`。没有新增人为副本限制；内存、存储和收益终止条件不变。
MILP 系数、约束、5 秒求解预算、0.01 相对间隙，以及贪心堆优先级、
候选遍历次序和版本失效规则均保持原样。DPMS 的任务调度器也未修改。

部署预测仍是原有独立链路近似；共享 NIC 由公共结算器执行，
没有将预测近似改成另一种算法，或通过放宽网络约束提速。

## 等价性验证

`tests/test_dpms_cost.py` 保留加速前的标量代价函数，仅用于测试。
检查内容包括：

- 1–5 阶段、32 节点的 200 组随机配置，每组比较 5 种候选部署，
  共 1,000 次代价计算，要求直接浮点相等而非宽容差；
- 零需求、无覆盖、不可达入口、全节点副本、相同代价及零工作量；
- 多次连续规划改变节点/链路负载、计算/数据倍数与请求负载，
  在内存约束生效时比较完整部署、副本数与目标值；
- 同一抽样 Episode 的部署、路由所产生的结算指标相同，
  只允许实际运行耗时不同。

这些检查覆盖代价计算和现有测试场景，不代表对所有可能输入的数学证明。
MILP 在极难实例上仍可能受墙钟求解预算影响，跨运行得到不同可行解；
本次没有改变或移除该旧有行为。

验证执行记录：全项目回归通过 283 项（315.14 秒）；随后补充最终结算
检查并强化内存受限测试，最新相关模块回归通过 40 项（5.51 秒），
其中代价与规划等价性测试共 9 项。原有训练回归没有出现失败。

## 实际规模测速

2026-10-13 在当前机器上，使用当前 Proposed 训练配置的物理环境
（种子 2026、32 节点、10 服务、基准负载 1.0、审计服务预算、共享 NIC），
独立执行一次旧标量代价实现和一次新实现的完整 `plan`。
两次均实际运行 MILP 和全部候选/副本搜索，不回放预存 MILP 解，
不设置候选或副本截断：

| 指标 | 旧标量实现 | 本次实现 |
| --- | ---: | ---: |
| 完整部署规划耗时 | 220.950 s | 10.058 s |
| 新增副本 | 467 | 467 |
| 总副本 | 496 | 496 |
| MILP 目标值 | 0.08212625111815612 | 0.08212625111815612 |
| 部署预测目标值 | 0.07099220246617116 | 0.07099220246617116 |

最终二元部署张量逐项相同，内存/存储可行性检查通过。
旧实现通过测试中的参考类，仅替换代价函数为冻结标量版本，
其余规划流程相同。规划提速约 **21.97 倍**，耗时减少约 **95.45%**。
机器当时有其他工作负载，因此这是单次实测，不是固定性能承诺。
两个目标值都是部署预测代理目标，不能当作实际评估的平均请求时延。

整轮评估还包含请求生成、任务调度、KKT 结算和写出，不能推断整个
五场景评估也提速 21.97 倍；其他负载点、节点资源和服务异质性也会影响耗时。
测速记录保存在 `results/diagnostics/dpms_acceleration_20261013/benchmark.json`。

## 使用与追溯

原来的五方案评估指令无需增加参数。新评估的 `metadata.json` 和
DPMS 部署诊断记录标记 `plan-local-home-vectorized-v1`。

已经启动的评估不会自动替换载入的 Python 代码，不中断已有进程。
之后重新启动的评估才采用本次实现；旧结果保持原样。
提速只改变评估等待时间，不保证任何方案的时延排名改变。

复核命令：

```powershell
python -m pytest tests/test_dpms_cost.py tests/test_comparison_algorithmic.py tests/test_comparison_runner.py -q
```
