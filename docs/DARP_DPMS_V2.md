## 两方案共有的需求驱动贪心部署

每个部署窗口重新规划，输入仅包括当前已知用户偏好、接入节点、服务参数、节点资源、链路和负载；不读取未来请求或评估结果。

记 `q[h,s]` 为归一化到全部用户的接入节点 h 对服务 s 的需求权重，`p[s]=sum_h q[h,s]`。
节点有效计算能力 `F[n]=physical_F[n]*clip(1-0.75*load[n],0.1,1)`，单位 Gcycle/s，与现有算法预测口径一致。

1. **覆盖优先。** 每个有效阶段至少部署一个副本。按阶段 RAM/全网最大节点 RAM 与 SSD/全网最大节点 SSD 的较大值降序处理，相同值按需求热度、服务和阶段顺序处理。
2. **节点选择。** 遍历全部尚未部署该阶段、RAM/SSD 可行且从需求接入节点可达的节点，最小化：

   `score(s,k,n) = sum_h q[h,s]*(path_propagation[h,n] + input_proxy[s,k]*sum_edges(1/B_effective)) + p[s]*C[s,k]/F[n]`。

   第一个阶段的 input_proxy 为服务上传量，其余阶段为前阶段输出量；数据量与计算量应用当前环境缩放系数。后续阶段仍从接入节点估计局部性，这是明确的近似，**没有进行完整服务链成本优化**。无线接入开销不进入节点排序，因为同一请求的该部分与边缘节点决策无关；真实评估仍计入。
3. **覆盖修复。** 若贪心装箱产生碎片、无法完成全部阶段的覆盖，从头求解零目标二元可行性问题。约束为各阶段恰一个副本、节点 RAM/SSD 及可达性；不包含时延目标。沿用原覆盖修复的 5 秒求解上限，仅限修复，不限制正常贪心搜索。找不到可行解时明确报错，不使用超预算部署。
4. **追加副本。** 对所有仍可部署的阶段计算 `priority=p[s]/replica_count[s,k]`，选择优先级最高的阶段，再选择该阶段局部 score 最小的可行节点；确定性平局按服务、阶段、节点顺序处理。重复直到没有有需求且可行的阶段—节点组合。

没有预设副本总数、固定 K 个候选节点、随机丢弃节点、额外资源折扣或按方案设置的计算预算。RAM/SSD 与 Proposed 使用同一个服务资源预算。独立节点上的同阶段副本均占实际 RAM/SSD。

与 legacy-v1 的区别是：DARP 不再用带时延目标的 MILP 求初始覆盖；DPMS 不再用完整链路递推成本选择追加副本。v2 使用相同的需求比例贪心部署，便于对照部署和调度的贡献。

## DARP：算法部署 + 冻结 Proposed Fast

部署使用上述方法。请求调度继续加载本轮 Proposed checkpoint 的 Fast PPO，动作模式由共同的 `--learned-fast-eval-mode` 控制，且 `record=False`，不训练、不更改权重、不调用其 Slow 部署决策。最终使用公共计算与网络 KKT 结算。

因此该方案主要对照部署层，但需注意学习到的 Fast 可能存在部署分布迁移，DARP 与 Proposed 的差距不能全部解释为 Slow 的孤立因果效应。

## DPMS：算法部署 + 逐阶段边际成本调度

部署与 DARP v2 完全相同。请求按当前批次原顺序处理；每个请求从第一阶段开始依次选择节点。

对当前阶段所有可部署节点，先进行**可达性剪枝**，排除无法通往任意后续有效节点的死路；不比较后续阶段的时延，不截断候选数量。对每个剩余节点估计当前传输与计算的边际成本：

`increment(d,S,F,m)=((S+m*sqrt(d))^2-S^2)/F`。

其中 d 是单请求计算量或传输量，m 为 request_count，S 是当前因果阶段、当前资源上此前请求的加权平方根需求和。路径还计入 `m*propagation`。计算及链路账本按串行阶段分离；选择后立即更新当前阶段账本，再处理下一阶段。

它与旧 DPMS 的区别是**逐阶段贪心而非整链动态规划**。节点容量、当前负载、数据量和已有批次需求都参与预测，没有人为惩罚项。

与旧版预测器相同，逐链路边际分数是共享 NIC 条件下的近似，不等于耦合 NIC 求解器的精确边际成本。最终全部请求仍交给公共、约束不变的 KKT 求解器结算，不能将预测分数当成真实测量时延。该限制必须在论文方案说明中披露。

## 结果追溯与比较规则

- `metadata.json` 记录 `baseline_implementation`、每方案实现版本与当前方案说明。
- 原始结果、失败记录、部署诊断和逐服务时延诊断均增加 `scheme_implementation` 字段。
- Phase 3 要求 Phase 2 的 DARP/DPMS 实现版本相同；旧记录没有版本字段时按 legacy-v1 解释。
- 每次运行使用新结果目录；不改写历史数值、归档或图像。单个目录的图例保持 DARP、DPMS；跨版本联合绘图时应额外标注版本。
- 不将 v2 与 legacy-v1 的 Hybrid 误称为使用相同调度器。Hybrid 本次不变，仍使用原整链边际成本调度。
- 共同场景、需求、checkpoint、随机种子、抽样、共享 NIC 和 KKT 精度均不得按方案修改。

## 使用

已有对比指令可继续使用，DARP/DPMS 默认采用 v2。为实验可复现，建议显式加入：

```powershell
--baseline-implementation demand-greedy-v2
```
